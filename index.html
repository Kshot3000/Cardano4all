Tools — right here, no wallet needed

Address inspector

Paste any Cardano address. Checks the bech32 checksum locally in your browser and tells you the address type and network. Nothing is sent anywhere.

ADA ⇄ lovelace converter

1 ADA = 1,000,000 lovelace. Exact integer maths (BigInt) — no floating-point rounding, works offline.

Epoch / slot calculator

Convert between Cardano mainnet slots and epochs, offline, from the fixed protocol parameters: Byron epochs held 21,600 slots of 20 seconds; since Shelley (epoch 208, slot 4,492,800) an epoch holds 432,000 slots of 1 second.

Staking rewards estimator

Model a stake at an annual rate you assume. A Cardano epoch is 5 days, so a year holds 73 epochs; the rate is split evenly across them and compounded each epoch in exact integer lovelace maths. A modelled estimate only — actual pool rewards vary with performance, saturation and fees, and are never promised.

Pool reward split calculator

How does one epoch's pool reward actually divide? By the ledger's own reward-sharing rule: the operator's fixed cost comes out first — if the rewards don't cover it, the operator takes them all and delegators get nothing that epoch — then the margin percentage of what remains goes to the operator, and the rest is shared by stake, the operator's own stake included, with each share floored to whole lovelace exactly as the ledger floors it. Enter a pool's figures to see the split for the operator and for one delegator. This divides a reward total you supply; it does not predict what a pool will earn, which depends on blocks minted, saturation and protocol parameters.

Transaction fee calculator

Cardano's minimum fee is a fixed protocol formula: 44 lovelace per byte of transaction size + 155,381 lovelace (mainnet parameters, checked against the live protocol parameters for epoch 660). Enter a transaction size — your wallet or cardano-cli reports it when building — and get the exact minimum in lovelace.

Size-based minimum only: transactions that run Plutus scripts also pay for execution units, and reference scripts add a per-byte charge, so real script transactions cost more than this floor.

Plutus execution cost calculator

The script part of a transaction's fee. When a transaction runs Plutus scripts, the ledger charges for their total execution units on top of the size fee: ⌈ memory × 0.0577 + steps × 0.0000721 ⌉ lovelace — one ceiling over the sum, exactly as the ledger defines it (mainnet prices, checked against the live protocol parameters for epoch 660). Enter the units your wallet, cardano-cli or an evaluator reports for a script — measuring a script to find its units is node work; this prices units you already have. A transaction's totals are capped at 16,500,000 memory units and 10,000,000,000 steps.

Reference script fee calculator

The reference-script part of a transaction's fee. Since the Conway era, a transaction that uses reference scripts pays for their total size in 25,600-byte tiers: the first tier costs 15 lovelace per byte (the current mainnet protocol parameter, checked against the live protocol parameters for epoch 660) and each following tier's per-byte price rises by a factor of 1.2 — the ledger's defence against oversized-script attacks, with the total floored once at the end. Every referenced script counts, duplicates included. Enter the total size of the reference scripts your transaction uses (your wallet or cardano-cli reports script sizes); the per-transaction limit is 204,800 bytes.

Total minimum fee calculator

All three parts of a transaction's minimum fee in one place — the ledger's minimum is their exact sum: the size fee (44 lovelace/byte + 155,381), the Plutus execution cost (⌈ memory × 0.0577 + steps × 0.0000721 ⌉) and the tiered reference script fee (15 lovelace/byte rising 1.2× per 25,600-byte tier), each computed by the proven calculators above with their own rounding exactly where the ledger puts it — the total itself is never rounded. Mainnet parameters, checked against the live protocol parameters for epoch 660. Leave the script fields at 0 for a plain transaction.

Ledger deposits calculator

Registering on chain takes a refundable deposit, charged once per registration at the current mainnet protocol parameters (checked against the live protocol parameters for epoch 660): a stake credential registration is 2 ADA, a new stake pool registration 500 ADA, a DRep registration 500 ADA and a governance action proposal 100,000 ADA. The total below is their exact sum — and deposits are not fees: they come back on deregistration, on pool retirement, or when a governance action is enacted or expires. Updating an existing pool charges no new pool deposit, and delegating on its own charges nothing.

Transaction ID calculator

A transaction's ID — the identifier every explorer shows — is blake2b-256 of the transaction body's CBOR bytes, and nothing else: the witness set, the is-valid flag and the auxiliary data are not part of it, so the ID is fixed before the transaction is signed. Paste the body's CBOR hex, or a whole transaction's CBOR hex (the array cardano-cli and wallets emit) and the body is taken out exactly as transmitted — never re-serialised. Computed locally; nothing is signed or sent.

Transaction inspector

Paste a transaction (or just its body) as CBOR hex — the form explorers, cardano-cli and wallets exchange — and read what it actually does before you trust it: every input it spends, every output with its address, lovelace, native assets (with CIP-14 fingerprints), datum and reference script, the declared fee, the validity interval, reward withdrawals, mints and burns, collateral, required signers and governance entries. Decoded locally against the Conway ledger format — body field numbering follows the ledger's own CDDL (the script data hash is key 11, collateral key 13, reference inputs key 18), and both output serialisations the ledger allows are understood. One honest limit: a body names its inputs by reference, so their amounts are not in the body and no balance or fee-sufficiency check is possible from the body alone — the fee shown is the fee the body declares. Nothing is signed or sent.

Value decoder

One transaction output's value on its own — the CBOR cardano-cli prints for an output amount and indexers store — decoded locally: the lovelace, and every native asset with its policy ID, asset name (as text when the name bytes are readable text), exact quantity and CIP-14 fingerprint. A value is a bare coin amount, or [coin, {policy: {name: quantity}}]; quantities in an output are always positive, and each asset appears exactly once. A mint's signed quantities and a whole output or transaction are different shapes — the transaction inspector above decodes those.

Transaction output decoder

One transaction output on its own — the CBOR a block, an indexer or cardano-cli carries for a single output — decoded locally: its address, lovelace and native assets (with CIP-14 fingerprints), its datum (hash or inline) and its reference script. Both serialisations the ledger allows are understood: the current Babbage map form {0: address, 1: value, 2: datum option, 3: script reference} and the older Alonzo array form. The address must be a Shelley payment address — a reward address is not an output address — quantities in an output are always positive, and no map key may repeat. A value alone is decoded by the value decoder above; a whole transaction by the transaction inspector.

Mint / burn decoder

One transaction's mint field on its own — body key 9, the map a transaction carries when it creates or destroys native assets — decoded locally: every asset with its policy ID, name (as text when the name bytes are readable text), signed quantity and CIP-14 fingerprint, labelled mint or burn. The ledger rule (Conway CDDL) is mint = {+ policy_id => {+ asset_name => nonzero_int64}}: at least one policy and one asset per policy, and every quantity a non-zero int64 — positive mints, negative burns, zero is not a legal entry. That sign rule is the opposite of an output value's, which is why this is its own decoder. Repeated policy or asset-name keys are rejected — a mint is a map. An output value is decoded by the value decoder above; a whole transaction by the transaction inspector.

Withdrawals decoder

One transaction's withdrawals field on its own — body key 5, the map a transaction carries when it takes staking rewards out of reward accounts — decoded locally: every reward account with its stake credential (key or script), network and exact amount in lovelace, plus the total. The ledger rule (Conway CDDL) is withdrawals = {+ reward_account => coin}: at least one entry, every key a Shelley reward address — a payment address is not a reward account — and every amount an unsigned coin amount. Unlike a mint field's quantities, a zero amount is a legal entry here: this field's rule is plain coin, not nonzero. Repeated accounts are rejected — a withdrawals field is a map. An output value is decoded by the value decoder above; a whole transaction by the transaction inspector.

Transaction inputs decoder

One transaction's inputs field on its own — body key 0, the set of UTxO references a transaction spends — decoded locally: every input in the familiar transaction-ID#index form, in the order encoded. The ledger rule (Conway CDDL) is transaction_input = [transaction_id, index] with a 32-byte transaction ID and an index that is a uint .size 2 (0–65,535), and the field is a set: serialised as a plain array or under CBOR set tag 258 — both forms decode here — with no reference repeated. A transaction must spend at least one output, so an empty set is rejected, and an index above 65,535 is rejected even though some libraries serialise one. The same reference shape is what the collateral and reference-inputs fields carry. A single output is decoded by the transaction output decoder above; a whole transaction by the transaction inspector.

Required signers decoder

One transaction's required signers field on its own — body key 14, the set of key hashes a transaction declares must sign it (native-script and Plutus witnesses are checked against this list) — decoded locally: every required signer's key hash, in the order encoded. The ledger rule (Conway CDDL) is required_signers = nonempty_set<addr_keyhash>: a non-empty set of 28-byte key hashes, serialised as a plain array or under CBOR set tag 258 — both forms decode here — with no hash repeated. The non-empty rule is in the grammar itself here (nonempty_set), unlike the inputs field above, whose empty rejection rests on the separate must-spend rule. A 32-byte transaction ID is not a key hash and is rejected. The inputs a transaction spends are decoded by the inputs decoder above; a whole transaction by the transaction inspector.

Reference inputs decoder

One transaction's reference inputs field on its own — body key 18, the UTxOs a transaction reads without spending (CIP-31: a script can see a referenced output's datum, and take a reference script from it, while the UTxO itself stays unspent) — decoded locally: every reference in the familiar transaction-ID#index form, in the order encoded. The entry shape is the inputs field's — transaction_input = [transaction_id, index], a 32-byte transaction ID and an index that is a uint .size 2 (0–65,535) — but the field rule differs in one word: the Conway CDDL makes this a nonempty_set, so an empty field is forbidden by the grammar itself, where the inputs field's empty rejection rests on the separate must-spend rule. Serialised as a plain array or under CBOR set tag 258 — both forms decode here — with no reference repeated (the same transaction at a different index is a different reference). The UTxOs a transaction spends are decoded by the inputs decoder above; a whole transaction by the transaction inspector.

Collateral inputs decoder

One transaction's collateral field on its own — body key 13, the UTxOs a script transaction puts at risk: if its Plutus scripts pass, the collateral is not spent; if a script fails, the ledger takes it as the fee — decoded locally: every entry in the familiar transaction-ID#index form, in the order encoded. The entry shape is the inputs field's — transaction_input = [transaction_id, index], a 32-byte transaction ID and an index that is a uint .size 2 (0–65,535) — and the Conway CDDL makes this field a nonempty_set, so an empty field is forbidden by the grammar itself. This field carries one more rule its siblings don't: at most 3 entries, the current max_collateral_inputs protocol parameter (checked against the live protocol parameters for epoch 660). Serialised as a plain array or under CBOR set tag 258 — both forms decode here — with no reference repeated (the same transaction at a different index is a different reference). The UTxOs a transaction spends are decoded by the inputs decoder above, the ones it only reads by the reference inputs decoder; a whole transaction by the transaction inspector.

Certificates decoder

One transaction's certificates field on its own — body key 4, the stake, pool, committee and DRep actions the transaction carries: registering or retiring a stake credential or pool, delegating stake or voting power, authorising a committee hot credential, registering a DRep — decoded locally, in the order encoded. The Conway CDDL makes the field a nonempty_oset (an ordered set, plain array or CBOR set tag 258), and all seventeen Conway certificate types decode (0–4 and 7–18; the old genesis and MIR types 5 and 6 don't exist in Conway and are rejected), each with its credential — a key hash or a script hash — its pool, its DRep (a key hash, a script hash, always abstain or always no confidence) and its deposit or refund where it carries one. A pool registration shows the full pool parameters: operator, VRF key hash, pledge, cost, margin, reward account, owners, every relay and the metadata pointer. The same certificate twice is rejected (it's a set — but the same credential in two different certificates is the normal register-and-delegate flow, and decodes). A whole transaction is decoded by the transaction inspector above.

Minimum-UTxO calculator

Every transaction output must carry a minimum amount of ADA, set by the ledger itself: (160 + the output's serialised size in bytes) × 4,310 lovelace at the current mainnet protocol parameter (coins_per_utxo_size, checked against the live protocol parameters for epoch 660). Native assets, datums and reference scripts all make an output bigger, so they raise its minimum. Describe the output below — this builds its exact serialised bytes locally and applies the ledger formula, it does not estimate from counts. A plain output to a base address needs 978,370 lovelace (0.97837 ADA).

Pool ID converter

A stake pool ID is a 28-byte hash shown two ways: 56 hex characters, or bech32 starting pool1…. Convert between them locally — explorers, pool tooling and cardano-cli each prefer a different form.

Asset fingerprint (CIP-14)

Every Cardano native asset has a short user-facing ID — the asset1… fingerprint explorers and wallets show. It is the bech32 form of the blake2b-160 hash of the policy ID followed by the asset name (CIP-14), computed locally here. One-way by design: a fingerprint identifies an asset but cannot be turned back into its policy ID and name.

Asset unit decoder

Data APIs identify a native asset by its unit — one long hex string: the policy ID followed directly by the asset name in hex. Paste a unit (from Blockfrost, Koios or cardano-cli) to split it back into the policy ID and the asset name — shown as text when the name bytes are readable text — plus its CIP-14 fingerprint, locally. An asset1… fingerprint is a one-way hash, not a unit, so it cannot be decoded this way.

Datum & script hashes

The two hashes Cardano developers reach for daily, computed locally. A datum hash is the blake2b-256 of a datum's CBOR bytes — what a transaction stores when it keeps the datum off-chain. A script hash is the blake2b-224 of a one-byte language tag plus the script bytes; for a minting script, that hash is its policy ID. For Plutus scripts, paste the flat script bytes (the compiledCode from an Aiken blueprint), not the CBOR-wrapped form some tools display.

CBOR / Plutus Data decoder

The read side of the hash tool above. Datums, redeemers and script parameters all travel as CBOR (RFC 8949) — explorers show the hex, but not what it means. Paste one CBOR item as hex to read its structure locally: integers decode exactly (no floating-point rounding, however large), byte strings show as h'…', and Plutus constructors show as Constr — d8799f182a182bff, the sample datum from the hash tool, reads as Constr 0 [42, 43]. Indefinite-length items (the style Plutus Data uses) are supported; truncated input and trailing bytes are rejected. Structure only — this does not check a datum against any script's schema.

Plutus Data encoder

The write side of the decoder above. Datums and redeemers are built as Plutus Data and shown across Cardano tooling in a standard JSON form — {"int": 42}, {"bytes": "deadbeef"}, {"list": […]}, {"map": [{"k": …, "v": …}]}, {"constructor": 0, "fields": […]}. Paste one value in that form to get its exact CBOR and its datum hash, locally: integers are exact at any size, byte strings over 64 bytes are chunked the way Plutus requires, and constructors use the tag forms current tooling uses (121+, 1280+ and tag 102). For example {"constructor":0,"fields":[{"int":42},{"int":43}]} encodes to the sample datum the hash tool uses, d8799f182a182bff.

Key hashes & address builder

Addresses are built from key hashes — the blake2b-224 hash of a public verification key — not from the keys themselves. Paste a payment verification key (and optionally a stake verification key) to get its key hash and the addresses it controls: the base address a wallet normally shows, the enterprise address (payment key only — it cannot earn staking rewards), and the reward address where staking rewards land. Everything is computed locally; this works on public verification keys only — never paste a private or signing key into any website, including this one.

Address builder — from credential hashes

The tool above starts from verification keys. This one starts one step later, from the credential hashes themselves — a payment or stake credential can be a key hash or a script hash, and which kind each part is decides the address type (CIP-19 types 0–3, 6–7, 14–15). The common script workflow: hash a Plutus script with the datum & script hash tool, paste the script hash here as a script payment credential, and get the enterprise script address its funds lock to — no key can spend from it, only the script can. A minting script's hash doubles as its policy ID. Everything is computed locally, offline.

Address decoder (CIP-19)

The builder above in reverse. Every Shelley address starts with a one-byte header — the address type in the high half, the network in the low half — followed by 28-byte credential hashes. Paste any base, pointer, enterprise or reward address to see its type, network and the payment and stake credential hashes inside it, plus the enterprise and reward addresses derived from those same hashes. Computed locally; Byron addresses predate this layout and are not decoded.

Address hex ⇄ bech32 converter

The same address travels in two forms: bech32 (addr1…) for people and explorers, and raw hex for machines — CIP-30 wallets hand dApps addresses as hex, and APIs and cardano-cli accept that hex form. Convert between them locally; it is a pure re-encoding of the identical address bytes, so nothing is gained or lost. Only valid Shelley addresses convert — the header byte and length are checked on the way in.

Governance ID converter (CIP-129)

Conway governance IDs — DRep IDs (drep1…), Constitutional Committee credentials (cc_hot1… / cc_cold1…) and governance action IDs (gov_action1…) — circulate in two encodings. The current CIP-129 form prepends a header byte naming the kind and whether the credential is a key hash or a script hash; the older CIP-105 form encodes the bare hash, with separate *_script prefixes. Some tools accept only one form. Paste either form (or the hex payload) and get both, locally.

Native script — policy ID & script address (multisig / timelock)

Native scripts are Cardano's built-in multisig and timelock rules — no Plutus, no contract audit: a script says which key signatures count (all / any / atLeast of a list) and the slots it is valid between (after / before). Paste one in the cardano-cli JSON form and get its policy ID — the script hash a minting script's assets live under — its exact CBOR, and the script address the script locks. Computed locally, offline, byte-for-byte the way the ledger serialises it.
